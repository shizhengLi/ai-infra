# 实验 075：动态请求集合下的 decode cursor

## 1. 问题

实验 073/074 的请求集合在多轮之间保持不变。真实服务中请求会完成、取消，也会有新 UID 加入。
073 保存的是 `batch.reqs` 的列表下标；当列表前部请求被移除时，同一个下标不再代表原来的
“下一个请求”，可能跳过一个尚未服务的 UID。

## 2. 基线反例

容量每轮最多容纳 2 个请求：

```text
第一轮集合: [0, 1, 2, 3] -> 选择 [0, 1]
移除 UID 0 后: [1, 2, 3]
旧下标 cursor=2 -> 错误选择 [3, 1]
```

第二轮跳过 UID 2，说明下标 cursor 对动态集合不稳定。

## 3. 实现

将 scheduler 状态从整数下标改为 `_decode_capacity_cursor_uid`：

1. 每次裁剪后保存“最后选中请求的后继 UID”。
2. 下一轮如果该 UID 仍存在，从它开始环形遍历。
3. 如果该 UID 已完成或取消，从当前集合中第一个 `uid >= cursor_uid` 的请求开始；没有更大
   UID 时自然回到列表头部。

这样 cursor 与请求身份绑定，不依赖列表长度和前部删除造成的索引漂移。

## 4. 结果

同一反例在新实现下：

```text
第一轮集合: [0, 1, 2, 3] -> 选择 [0, 1]
移除 UID 0 后: [1, 2, 3] -> 选择 [2, 3]
```

新增测试还覆盖 cursor 指向的 UID 被删除、UID 集合缩短后的行为。focused cache/scheduler tests
通过 13/13，完整 `tests/core` 回归结果为 119/119。

## 5. 结论

实验 075 通过动态 membership fairness/correctness gate。该修复不改变完整 batch 快路径和
容量判断，只提高容量受限时 cursor 的身份稳定性。下一步应在线记录请求完成/取消交错时的等待
轮数，并确认新 UID 不会因为 cursor 长期落后而出现尾延迟异常。
